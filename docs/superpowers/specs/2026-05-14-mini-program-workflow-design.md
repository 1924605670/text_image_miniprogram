# 小程序产品协作工作流设计

## 背景与目标

当前项目处于功能不完善阶段，需要先建立产品经理、开发人员、测试人员、运维人员之间的协作闭环，再逐步把这套流程开发成小程序内的任务流转能力。

目标是分阶段完成：先用规范统一协作方式，再开发最小可用的任务流转功能，最后补齐测试记录、发布记录和小程序测试版本验收能力。

## 推荐方案

采用“先流程规范，后系统化落地”的分阶段闭环方案。

第一阶段形成流程规范和任务模板，让团队可以立即按统一方式推进。第二阶段在系统内开发需求、开发、测试、发布、验收的最小流转能力。第三阶段补齐测试记录、发布检查清单、小程序测试版发布记录和验收看板。

该方案比只写规范更可追踪，比一次性开发完整项目管理系统更轻量，能避免偏离当前小程序产品核心功能。

## 角色职责

### 产品经理

产品经理维护需求池，编写需求说明，定义业务目标、功能范围、验收标准和优先级。需求开发完成、测试通过并发布到小程序测试版本后，产品经理负责最终验收。

### 开发人员

开发人员领取开发任务，实现功能，提交代码，填写自测说明，并在自测通过后提交测试。

### 测试人员

测试人员根据需求验收标准执行测试，记录测试通过、失败、缺陷说明和复测结果。测试失败时，任务回到开发人员处理。

### 运维人员

运维人员负责服务器部署、小程序测试版本提交、版本号确认、发布说明记录和回滚说明记录。发布完成后，任务进入产品验收环节。

## 主状态流

整体流程为：

`产品规划 → 需求确认 → 开发中 → 开发自测 → 测试中 → 测试通过 → 运维发布 → 小程序测试版可验收`

每个任务都必须记录需求标题、业务目标、功能范围、验收标准、负责人、当前状态、测试记录和发布记录。

## 系统功能模块

### 需求池

产品经理创建和维护需求。字段包括标题、背景、目标、优先级、范围、验收标准和期望版本。

需求状态包括草稿、待确认、已确认、暂缓。未填写验收标准的需求不能确认，未确认的需求不能进入开发。

### 开发任务

开发任务从已确认需求拆分而来。字段包括任务说明、开发负责人、关联需求、开发状态、自测说明和代码提交记录。

开发状态包括待开发、开发中、待自测、自测通过、提交测试。未填写自测说明的开发任务不能提交测试。

### 测试任务

测试人员处理已提交测试的任务。字段包括测试用例、测试结果、缺陷说明和复测结果。

测试状态包括待测试、测试中、测试失败、复测中、测试通过。测试失败必须回到开发任务处理，测试通过后才能进入发布任务。

### 发布任务

运维人员基于测试通过的功能创建发布单。字段包括服务器部署结果、小程序测试版本提交结果、版本号、发布说明和回滚说明。

发布状态包括待发布、发布中、已提交测试版、发布失败。未测试通过的功能不能创建发布任务。

### 验收看板

产品经理通过验收看板查看当前版本所有需求状态。看板展示本版本需求、开发进度、测试结果、发布记录和遗留问题。

小程序测试版提交成功后，产品经理才能进行最终验收。

## 数据流

1. 产品经理创建需求，需求进入需求池。
2. 需求确认后，拆分为一个或多个开发任务。
3. 开发人员完成开发并自测通过后，提交测试任务。
4. 测试人员测试通过后，任务进入发布任务。
5. 运维人员部署服务器并提交微信小程序测试版本。
6. 产品经理在验收看板确认测试版本是否满足需求。

## 关键验收规则

- 未确认的需求不能进入开发。
- 未填写验收标准的需求不能确认。
- 未填写自测说明的开发任务不能提交测试。
- 测试失败必须回到开发任务处理。
- 未测试通过的功能不能进入发布任务。
- 发布任务必须记录服务器部署结果和小程序测试版本提交结果。
- 小程序测试版提交成功后，产品经理才能做最终验收。

## 测试策略

开发自测覆盖功能主流程、异常输入和接口错误处理。

测试人员测试覆盖需求验收标准、重点回归流程和小程序兼容性检查。

运维发布验证覆盖服务器服务可访问、小程序测试版可打开、关键接口可用。

产品验收确认业务目标和用户体验满足需求。

## 阶段性交付

第一阶段交付流程规范、任务模板和角色职责说明。

第二阶段开发需求池、开发任务、测试任务、发布任务和验收看板的最小可用版本。

第三阶段补齐测试记录、发布检查清单、版本记录、缺陷闭环和最终验收记录。
